# 🔧 תיקון מיידי: Salesforce HTTP 400 `invalid_grant` — מדריך ביצוע מלא

> **סטטוס:** DRAFT לאישור אלון | עדיפות: P0 | ערוץ: CRM / Salesforce Integration
> **מטרה:** לשחזר חיבור OAuth מלא בין integration tool של UPE לבין Salesforce — כתנאי סף לכל דיווח שיווקי.

---

## 📋 רקע: מה קורה כאן?

שגיאת `invalid_grant` מתרחשת כאשר Salesforce דוחה את ה-authorization code או ה-refresh token בשלב החלפת הטוקן. זו שגיאת OAuth 2.0 גנרית שמציינת שהטוקן אינו תקף עוד.

השגיאה הספציפית שמופיעה:
```json
HTTP/1.1 400 Bad Request
{
  "error": "invalid_grant",
  "error_description": "authentication failure"
}
```

## 🔍 אבחון: סיבות שכיחות (ממוינות לפי סבירות)

| # | סיבה | בדיקה מהירה |
|---|------|-------------|
| 1 | **הסיסמה של ה-integration user שונתה** | בדוק מתי שונתה הסיסמה לעומת מועד תחילת השגיאה |
| 2 | **ה-refresh token פג / בוטל ידנית** | ראה סעיף 2 בהמשך |
| 3 | **IP Restriction חוסמת את הבקשה** | ראה סעיף 3 בהמשך |
| 4 | **OAuth Scope חסר (`refresh_token`)** | ראה סעיף 4 בהמשך |
| 5 | **Base URL שגוי (Production vs. Sandbox)** | ראה סעיף 1 בהמשך |
| 6 | **Refresh Token Rotation (RTR) הופעל** | ראה סעיף 5 בהמשך |
| 7 | **ה-integration user הושבת בארגון** | ראה סעיף 6 בהמשך |

## ✅ Checklist — בצע לפי הסדר

### שלב 1: וודא את ה-Base URL

בדוק תחילה שה-base URL נכון — זהו התיקון הקל ביותר. אם ה-base URL נכון והשגיאה נמשכת, עבור לשלב הבא.

- **Production:** `https://login.salesforce.com/services/oauth2/token`
- **Sandbox:** `https://test.salesforce.com/services/oauth2/token`

> ⚠️ שימוש ב-`login.salesforce.com` בסביבת Sandbox (או להפך) יגרום תמיד ל-`invalid_grant`.

---

### שלב 2: בדוק אם ה-Refresh Token בוטל / פג

**נתיב ב-Salesforce Setup:**
```
Setup → Quick Find: "OAuth" → OAuth Connected Apps Usage
```

Refresh token יכול לשמש ללא הגבלת זמן, אלא אם המשתמש או מנהל Salesforce ביטלו אותו. ניתן לבטל טוקנים בדף פרטי המשתמש תחת OAuth Connected Apps, או בדף OAuth Connected Apps Usage בהגדרות.

**בדיקה:**
1. Setup → Users → [שם ה-integration user]
2. גלול לסעיף "OAuth Connected Apps" — בדוק אם האפליקציה מופיעה
3. אם היא אינה מופיעה — הטוקן בוטל, יש לבצע **Re-authentication**

---

### שלב 3: טפל ב-IP Restrictions

אם הארגון אוכף הגבלות IP והמשתמש מתחבר מ-IP שאינו מורשה, יש לצרף את ה-Security Token לסיסמה. ניתן לאפס את ה-Security Token דרך: Personal Settings → Reset My Security Token.

**אופציה מהירה לפתוח חסימת IP:**
ב-Connected App → Manage Connected Apps → [שם האפליקציה] → Edit Policies, תחת Permitted Users, בחר "All users may self-authorize" ושמור.

**אופציה מאוזנת יותר (מומלצת לייצור):**
```
Setup → Connected Apps → Manage Connected Apps → [App] → Edit Policies
→ IP Relaxation: "Relax IP restrictions"
```

---

### שלב 4: וודא OAuth Scopes בכל Connected App

**נתיב:**
```
Setup → App Manager → [שם האפליקציה] → Edit → OAuth Settings
```

**Scopes חובה עבור integration שיווקי:**
| Scope | תיאור |
|-------|--------|
| `api` | גישה ל-API |
| `refresh_token, offline_access` | מאפשר שימוש ב-refresh token |
| `full` | גישה מלאה (אם רלוונטי) |

יש לוודא שה-`refresh_token` scope מופעל ב-Connected App ב-Salesforce.

> ⚠️ לאחר שמירת שינויים ב-Connected App — המתן **10–15 דקות** לפני ניסיון חיבור חוזר.

---

### שלב 5: בדוק אם Refresh Token Rotation (RTR) הופעל

Refresh tokens הניתנים לשימוש חוזר מרובה יוצרים פגיעות אבטחה. Salesforce הציגה Refresh Token Rotation (RTR) כמנגנון הגנה — הגדרה זו אוכפת שימוש חד-פעמי ב-refresh token על ידי הנפקת טוקן חדש בכל החלפה וביטול מיידי של הישן.

לאחר שה-refresh token עבר rotation, ניסיון לממש את הישן נתפס כעדות לגנבת טוקן, ו-Salesforce מבטל כל ה-refresh tokens הפעילים עבור אותו user-app pair.

**בדיקה:**
```
Setup → External Client Apps (או Connected Apps) → [האפליקציה] → Policies → OAuth Policies
→ בדוק: "Refresh Token Rotation" — Enabled/Disabled?
```

אם RTR מופעל ואין תמיכה בו ב-integration — **כבה RTR** (זמנית) או עדכן את הקוד לתמוך בו.

---

### שלב 6: וודא שה-Integration User פעיל

אם המשתמש הושבת בארגון Salesforce, תקבל את אותה הודעת שגיאת אימות בדיוק.

```
Setup → Users → [שם ה-integration user]
→ וודא שה-checkbox "Active" מסומן
```

---

### שלב 7: בצע Re-authentication מלא (הפתרון הכולל)

הפתרון הסופי הוא לבצע re-authentication. Salesforce מבטל את כל ה-access tokens וה-refresh tokens של המשתמש כאשר הוא משנה את הסיסמה.

**נוהל Re-Authentication — שלב אחרי שלב:**

```
1. [Salesforce] Setup → Connected Apps → Manage Connected Apps
   → [האפליקציה] → בדוק ש-Policies תקינות (ראה שלבים 3–5)

2. [Salesforce] ביטול ה-token הקיים:
   Setup → Users → [integration user] → OAuth Connected Apps
   → לחץ "Revoke" על האפליקציה הרלוונטית

3. [Integration Tool — HubSpot / Make / Zapier / custom]:
   → כנס להגדרות ה-Salesforce integration
   → לחץ "Disconnect" / "Re-connect" / "Re-authorize"
   → התחבר עם אישורי ה-integration user

4. לאחר החיבור — בצע בדיקת smoke test:
   → וודא שרשומת Lead מסוג test עוברת ל-Salesforce
   → וודא שה-Lead Source מיוחס נכון
```

## 🆕 הערת Spring '26 — חשוב לדעת

יצירת Connected Apps חדשות מוגבלת החל מ-Spring '26. ניתן להמשיך להשתמש ב-Connected Apps קיימים לאחר Spring '26, אך Salesforce ממליצה לעבור ל-External Client Apps במקום.

> ✅ **לUPE:** אם החיבור הקיים הוא Connected App ישן — אין צורך להסיר אותו. הוא ממשיך לפעול. פשוט לבצע re-auth ולא ליצור Connected App חדש.

## 🧪 בדיקת חיבור — cURL לאחר תיקון

לאחר ביצוע Re-authentication, ניתן לאמת את הטוקן החדש ידנית:

```bash
curl -X POST https://login.salesforce.com/services/oauth2/token \
  -d "grant_type=refresh_token" \
  -d "client_id=YOUR_CONSUMER_KEY" \
  -d "client_secret=YOUR_CONSUMER_SECRET" \
  -d "refresh_token=YOUR_NEW_REFRESH_TOKEN"
```

**תשובה תקינה צריכה להראות:**
```json
{
  "access_token": "00D...",
  "instance_url": "https://yourorg.salesforce.com",
  "id": "https://login.salesforce.com/id/...",
  "token_type": "Bearer",
  "issued_at": "...",
  "signature": "..."
}
```
