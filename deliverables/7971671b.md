## מה קורה ומדוע זה קריטי

שגיאת `HTTP 400 Bad Request` עם `"error": "invalid_grant"` היא שגיאת OAuth שמחזיר Salesforce כאשר אינו יכול לאמת את הטוקן. **בפועל עבור UPE:** כל הלידים שנכנסים דרך האתר, LinkedIn, ומסעות הדיוור — אינם נרשמים ב-CRM. ה-Scorecard עיוור. 10 לידים/חודש = מטרת הבסיס — לא ניתנת למדידה.

## שלב 0 — אבחון: מה בדיוק גרם לשגיאה?

לפני הכל, יש לזהות את שורש הבעיה. ב-Salesforce קיימות **5 סיבות עיקריות** לשגיאה זו:

| # | סיבה | אות-זיהוי |
|---|------|-----------|
| A | **טוקן פג תוקף / בוטל** | שגיאה שמופיעה לפתע לאחר תקופת פעילות תקינה |
| B | **שינוי סיסמה של ה-Service User** | השגיאה הופיעה מיד לאחר שינוי סיסמה |
| C | **מדיניות "Immediately expire refresh token"** | השגיאה קבועה, לא אפיזודית |
| D | **IP Restriction — שרת לא ב-Whitelist** | השגיאה לפי IP/סביבה ספציפית |
| E | **Connected App בוטל ידנית ע"י Admin** | כל ה-API calls נכשלות בו-זמנית |

שגיאת `invalid_grant` מופיעה לרוב עקב טוקנים שפגו, חוסר התאמה ב-redirect URI, או אי-התאמות באוטורייזציה.

## שלב 1 — בדיקה מהירה (5 דקות) לפני כל תיקון

### ✅ רשימת בדיקה ב-Salesforce Setup

```
Salesforce Setup → Apps → App Manager → [שם ה-Connected App של UPE]
```

**בדוק את הפריטים הבאים בסדר:**

```
□ 1. OAuth Policies → Refresh Token Policy
      ↳ חייב להיות: "Refresh token is valid until revoked"
      ↳ אם מוגדר "Immediately expire" — זו הבעיה. שנה מיידית.

□ 2. OAuth Policies → Permitted Users
      ↳ חייב להיות: "All users may self-authorize"
         או: "Admin approved users are pre-authorized" + הפרופיל הנכון ✓

□ 3. OAuth Scopes — ודא שהסקופים הבאים מופעלים:
      ↳ api
      ↳ refresh_token / offline_access
      ↳ id

□ 4. Callback URL (redirect_uri)
      ↳ חייב להתאים בדיוק למה שמוגדר ב-integration
      ↳ כולל http/https, trailing slash, port

□ 5. IP Restrictions (Security Controls → Network Access)
      ↳ ודא שה-IP של שרת ה-Integration של UPE ב-Whitelist
```

הגדרת "Allow OAuth Username-Password Flows" חייבת להיות מופעלת תחת OAuth Policies של ה-Connected App — גם אם IP Relaxation ו-User Authorization מוגדרים נכון.

חובה לכלול את `refresh_token` או `offline_access` ב-OAuth 2.0 scope בבקשת האוטורייזציה — אחרת הטוקן לא יחודש.

## שלב 2 — תיקון מהיר: חידוש OAuth Token (זמני, ~15 דקות)

> **מתי לבצע:** כאשר הסיבה היא B (שינוי סיסמה) או E (ביטול ידני)

Salesforce מבטל את כל ה-Access Tokens וה-Refresh Tokens של המשתמש כאשר הוא משנה סיסמה — ואין אפשרות לבטל התנהגות זו.

### נוהל חידוש Token ידני:

```bash
# 1. קבל authorization code חדש דרך דפדפן:
GET https://login.salesforce.com/services/oauth2/authorize
  ?response_type=code
  &client_id=[CLIENT_ID_של_UPE]
  &redirect_uri=[REDIRECT_URI_המוגדר]
  &scope=api%20refresh_token%20id

# 2. עם ה-code שהתקבל, בצע token exchange:
POST https://login.salesforce.com/services/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=[CODE_שהתקבל]
&client_id=[CLIENT_ID]
&client_secret=[CLIENT_SECRET]
&redirect_uri=[REDIRECT_URI]

# 3. שמור את refresh_token החדש ב-Secret Manager / Env Variable
```

**⚠️ אזהרה:** ודא שלוגיקת ה-retry מבדילה בין שגיאות שניתן להתאושש מהן (timeout, 5xx) לבין כאלו שלא (400 Bad Request עם invalid_grant). **לעולם אל תעשה retry אוטומטי על תגובת 400.**

## שלב 3 — תיקון מבני (מומלץ): מעבר ל-JWT Bearer Flow

> **מדוע זה הפתרון הנכון לטווח ארוך:**

עבור Server-to-Server integration, לא כדאי להסתמך על credentials של משתמש ספציפי — שכן ניתן לבטלו, לנעול אותו, או להקפיאו בכל עת. ה-OAuth 2.0 JWT Bearer Flow מיועד לדיוק לזה — ומשתמש בסרטיפיקט לחתימת הבקשה ללא interaction של משתמש.

בשנת 2026, Salesforce מגביל יצירת Connected Apps חדשים החל מ-Spring '26 וממליצה על מודל External Client App לאינטגרציות חדשות.

### הוראות הגדרה — JWT Bearer Flow:

#### א. יצירת Certificate (מבצעים פעם אחת):

```bash
# הרץ בטרמינל (macOS/Linux):
openssl req -newkey rsa:2048 -nodes \
  -keyout upe_salesforce_key.pem \
  -x509 -days 730 \
  -out upe_salesforce_cert.pem \
  -subj "/C=IL/ST=Tel Aviv/O=UPE/CN=upe-salesforce-integration"

# שמור את שני הקבצים במקום מאובטח בלבד (לא ב-repo!)
```

#### ב. הגדרה ב-Salesforce Setup:

```
Setup → Apps → App Manager → [Connected App של UPE] → Edit

1. תחת "API (Enable OAuth Settings)":
   ✓ Enable OAuth Settings = ON
   ✓ Use digital signatures = ON
   ← העלה את קובץ upe_salesforce_cert.pem

2. OAuth Scopes:
   ✓ Manage user data via APIs (api)
   ✓ Perform requests at any time (refresh_token, offline_access)
   ✓ Access the identity URL service (id)

3. OAuth Policies:
   ✓ Permitted Users: Admin approved users are pre-authorized
   ✓ Refresh Token Policy: Refresh token is valid until revoked
   ✓ IP Relaxation: Relax IP restrictions (לסביבת production בלבד)

4. Pre-authorize the service user:
   Setup → Manage Connected Apps → [App] → Manage Profiles
   ← הוסף את הפרופיל של Service Account / API User
```

#### ג. קוד לקבלת Access Token (Python — ל-integration server):

```python
import jwt
import time
import requests
import json

# =========================================================
# UPE Salesforce JWT Bearer Token Flow
# שמור את הערכים האלו ב-ENV VARIABLES — לא בקוד!
# =========================================================

CONSUMER_KEY    = "YOUR_CONNECTED_APP_CONSUMER_KEY"
USERNAME        = "upe-api-service@yourdomain.com"
PRIVATE_KEY_PATH = "/secure/path/upe_salesforce_key.pem"
SF_LOGIN_URL    = "https://login.salesforce.com"  # prod
# SF_LOGIN_URL  = "https://test.salesforce.com"   # sandbox

def get_salesforce_access_token():
    """
    מחזיר access token תקף ל-Salesforce API.
    אין צורך ב-refresh token — JWT חדש נוצר בכל פעם.
    """
    with open(PRIVATE_KEY_PATH, "r") as f:
        private_key = f.read()

    payload = {
        "iss": CONSUMER_KEY,
        "sub": USERNAME,
        "aud": SF_LOGIN_URL,
        "exp": int(time.time()) + 300  # תוקף 5 דקות
    }

    encoded_jwt = jwt.encode(payload, private_key, algorithm="RS256")

    response = requests.post(
        f"{SF_LOGIN_URL}/services/oauth2/token",
        data={
            "grant_type": "urn:ietf:params:oauth:grant-type:jwt-bearer",
            "assertion": encoded_jwt
        },
        headers={"Content-Type": "application/x-www-form-urlencoded"}
    )

    if response.status_code == 200:
        token_data = response.json()
        print(f"✅ Token OK — Instance: {token_data.get('instance_url')}")
        return token_data["access_token"], token_data["instance_url"]
    else:
        error = response.json()
        print(f"❌ Token Error: {error}")
        raise Exception(f"Salesforce JWT auth failed: {error}")


# שימוש:
# access_token, instance_url = get_salesforce_access_token()
# headers = {"Authorization": f"Bearer {access_token}"}
```

OAuth 2.0 JWT Bearer Flow משמש לאינטגרציות Server-to-Server — הוא משתמש בסרטיפיקט לחתימת בקשת ה-JWT, ואינו מצריך interaction מצד המשתמש.

## שלב 4 — בדיקת חיבור עם Postman (ולידציה לפני production)

```
1. פתח Postman → New Request → POST
   URL: https://login.salesforce.com/services/oauth2/token
   
   Body (x-www-form-urlencoded):
   grant_type  = urn:ietf:params:oauth:grant-type:jwt-bearer
   assertion   = [JWT שנוצר בשלב ג]

2. שלח → ציפי ל:
   200 OK + { "access_token": "...", "instance_url": "https://[org].salesforce.com" }

3. בדיקת חיבור ל-CRM:
   GET https://[instance_url]/services/data/v59.0/sobjects/Lead/
   Authorization: Bearer [access_token]
   → ציפי לרשימת Leads = חיבור תקין ✅
```

השתמש ב-Postman לאימות שהאוטנטיקציה עובדת כהלכה לפני ה-production deploy.

## שלב 5 — מניעה לעתיד: Best Practices לאחר התיקון

ודא שמדיניות ה-OAuth refresh token **אינה** מוגדרת כ-"Immediately expire refresh token" — ועדיף להגדיר lifetime ארוך ככל האפשר לטוקן.

| פעולה | מה | מדוע |
|-------|-----|-------|
| **Service Account ייעודי** | צור user `upe-api@yourdomain.com` שהוא API-only | לא נפגע משינויי סיסמה של עובדים |
| **Env Variables** | Client Secret, Private Key — **רק ב-Secret Manager** | לא ב-repo, לא ב-code |
| **Token Monitoring** | Log כל `invalid_grant` ב-production + alert לאלון | גילוי מוקדם לפני עיוורון ה-CRM |
| **Token Expiry Pre-check** | בדוק תוקף token לפני כל API call | מונע 400 errors |
| **Sandbox vs. Production** | `login.salesforce.com` (prod) / `test.salesforce.com` (sandbox) — לעולם אל תערבב | שגיאה נפוצה שגורמת ל-400 |

Salesforce עלולה לחסום בקשות token מ-IPs לא מורשים אם מדיניות IP Restriction מופעלת בארגון — הוסף את ה-IP של שרת ה-Integration ל-Whitelist תחת `Setup → Security Controls → Network Access`.
